## 1. Task ID and Title

**C1 — Neo4j Schema (Constraints & Indexes)**

## 2. Track

Track C (see DOC4 §3 for the full track description and DOC4 §1 for where this track fits in the overall dependency structure).

## 3. Objective

Create uniqueness constraints and indexes for every ID field in DOC3 §1.13 and every node/relationship type in §6.1/§6.2.

## 4. Why This Task Exists

Enforces ID-uniqueness invariants at the database level, not just in application code.

## 5. Dependencies

A4

## 6. Relevant DOC1/DOC2/DOC3 Sections

- DOC3 §6.1 (node types, both CanonicalEntity and workspace/structural)
- DOC3 §6.2 (relationship types)
- DOC3 §1.13 (ID uniqueness scopes)

## 7. Inputs

- The full node/relationship type list from DOC3 §6

## 8. Expected Outputs

- Applied Neo4j schema (constraints + indexes)

## 9. Files/Modules to Create or Modify

- backend/app/graph/schema.py

## 10. Exact Interfaces/Contracts to Follow

- Uniqueness constraints on: entity_id, relationship_id, evidence_id, decision_id, finding_id, case_id, note_id, edge_ref_id (all globally unique per §1.13); a composite uniqueness on (record_id, dataset) since record_id is dataset-scoped.

## 11. Implementation Requirements

- Schema application must be idempotent — safe to re-run against an already-schema'd database.
- Cover both CanonicalEntity node types (Person...Event) and workspace/structural/derived types (Case, Evidence, Note, EdgeRef, ResolutionDecision, Finding) per the DOC3 §6.1 split.

## 12. Acceptance Criteria

- The schema-apply script runs cleanly against both an empty database and one that already has the schema applied.

## 13. Tests Required

- A test asserting the applied constraint list matches DOC3 §1.13's ID scope table exactly.

## 14. Definition of Done

Schema is applied to a dev Neo4j instance without error.
