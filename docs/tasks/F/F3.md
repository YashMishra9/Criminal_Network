## 1. Task ID and Title

**F3 — Query Execution, Evidence Attachment & Narration**

## 2. Track

Track F (see DOC4 §3 for the full track description and DOC4 §1 for where this track fits in the overall dependency structure).

## 3. Objective

Execute validated queries, attach evidence via C4, then call LLMClient a second time for narration-only-over-results.

## 4. Why This Task Exists

Second half of the two-call design — the structural guarantee that the LLM never originates a factual claim (Contract Invariant 3).

## 5. Dependencies

F2, C4

## 6. Relevant DOC1/DOC2/DOC3 Sections

- DOC2 §12 (two-call design)
- DOC3 §15 Invariant 3

## 7. Inputs

- A validated GeneratedQuery

## 8. Expected Outputs

- A narrated, evidence-attached result (the 'ok' case of AskResponse)

## 9. Files/Modules to Create or Modify

- backend/app/ask/service.py
- backend/app/ask/narrator.py

## 10. Exact Interfaces/Contracts to Follow

- GraphQueryResult {entities, relationships, paths}
- NarrationInput {question, query_result} -> NarrationOutput {narration}

## 11. Implementation Requirements

- The narration LLM call must receive ONLY query_result (plus the original question) as context — no independent graph or tool access whatsoever.
- Evidence must be attached via C4's EvidenceResolver before narration, not after.

## 12. Acceptance Criteria

- A code-review-verifiable confirmation that the narration prompt is constructed from query_result and the question only.
- A controlled-fixture test confirming the narration never mentions an entity absent from query_result.

## 13. Tests Required

- Unit test asserting narrator input isolation (no extra context passed).
- Integration test running the full generate -> validate -> execute -> narrate flow end-to-end.

## 14. Definition of Done

The two-call design is verifiably correct — the narration step cannot introduce unfounded facts.
